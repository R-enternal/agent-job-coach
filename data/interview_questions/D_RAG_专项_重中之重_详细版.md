# D · RAG 专项（重中之重，详细版）

RAG 是面试官最可能深挖的模块。下面按"全链路 → 切块 → 多格式解析 → 检索 → 向量库优化 → 评测"层层讲透。

一次检索 = 召回（retrieve）→ 排序（rank） 两步：


`
问题 → 【召回】从几万个片段里捞出一批候选(top-20)
     → 【排序】给候选排谁最相关 → 取 top-4 → 生成回答
`

- 召回的目标是"别漏" （recall：正确答案在不在候选里）；

- 排序的目标是"别错" （precision：前排是不是最相关的）。

为什么召回率难提升： 召回阶段用的是"快但粗"的手段，粗筛就可能把正确答案漏在候选之外——后面排序再好也没用。所以提高召回的核心是"让召回手段别漏"，下面 D4~D5 都是围绕这个。

三阶段：

- 索引（离线） ：文档清洗 → 切块 → embedding 向量化 → 写入向量库（带元数据）；

- 检索（在线） ：问题 embedding → 相似度 top-k → 组装上下文；

- 生成 ：上下文 + 问题 → LLM 只依据资料回答。

质量链条： 检索决定"材料在不在场"，生成决定"用得好不好"—— RAG 效果上限由检索决定，先优化检索。


`
flowchart LR
  subgraph IN["入库（一次）"]
    UP["上传文档"] --> SPLIT["结构感知切块"]
    SPLIT --> EMB["embedding 向量化"]
    EMB --> CHROMA[("向量库")]
  end
  subgraph SE["检索（每次提问）"]
    Q["问题"] --> QEMB["问题向量化"]
    QEMB --> TOP["相似度 top-k"]
    TOP --> CTX["组装上下文(带来源)"]
    CTX --> LLM["LLM 生成"]
  end
  CHROMA -. 读取 .-> TOP
`

硬切的病： 按每 500 字撕书，答案可能被撕成两半，或两个话题混进一个碎片。检索时"碎片语义不完整"→ 找不到答案（召回低）或找到一堆噪声。

解法：两层设计。 解析层把各种格式变成"带结构的语义单元"（标题/段落/表格/列表），切块层基于语义单元切，而不是对着原始字符串数长度。

切块层三原则：

- 语义单元优先 ：小单元按标题父子关系合并，大章节再拆；

- 表格/代码整体保留 ：切碎表格=毁语义；

- 中文分隔符 ： ["\n\n","\n","。","；","！","？","，"," "] ——能按段落切就按段落，再按句子、逗号，最后才按字符，保证句子不被劈开。

元数据增强： 每块带 doc_type、章节路径、页码、来源——检索可按类型/章节过滤，回答能引用到具体章节页码。

总体思路：先判类型，再分层解析。

扫描件 OCR 的关键： ①先图像预处理（去噪、二值化、倾斜矫正）；②OCR 后保留每个文字块的 bbox——双栏恢复和"引用到第几页"都靠它；③OCR 错字影响检索，可用模糊匹配/评测集量化。

项目进度（诚实版）： ✅ 文字型 PDF（带页码）+ 表格提取 + 扫描件检测提示，以及 md/docx/json/csv/xlsx/html 全部上线；⏳ OCR 接入、双栏恢复是规划项。

向量检索（语义找） ：embedding 模型把文本映射成高维向量，语义相近的向量距离近（余弦相似度衡量）。检索时把问题也变向量，和库里所有片段向量算相似度取 top-N。

- 优点 ：抓同义改写——"电机发热"能命中"温度过高"，字面完全不同也能找到；

- 缺点 ：精确数字/型号排不准。问"7.1mm/s"，向量觉得"振动值"相关片段都差不多，把最精确的排到后面。

BM25（关键词找） ：纯词法打分，两个核心因子：

- 词频 TF ：片段里这个词出现越多越相关；

- 逆文档频率 IDF ：越稀有的词权重越高（"7.1"全库少见，命中权重极大；"设备"到处都有，权重很低）。

打分 = 对问题每个词把 TF×IDF 加总。它"认字不认义"——字面一模一样才加分，所以精确词一抓一个准，但换说法就不认。

RRF 融合（两个榜单怎么合并） ：向量和 BM25 的 分数不是一个量纲 （一个相似度 0~1、一个词频加权分），不能直接相加。RRF 不比分数、比名次：


`
融合分(片段) = 1/(60 + 向量榜名次) + 1/(60 + BM25榜名次)
`

- 名次越靠前贡献越大； 两个榜单都靠前的片段融合分最高 ；

- 为什么是 60：一个约定俗成的平滑常数，让"第一名"和"第二名"差距别太大、又不至于让靠后名次完全没贡献；

- 好处：不需要分数归一化，对异常分数鲁棒。

项目实现： search() 里向量取 top-20、BM25 取 top-20，RRF 合并后再取前 4。BM25 是自实现的（没装 rank_bm25 依赖），中文分词用"英文/数字词 + 汉字二元组"做近似。


`
flowchart LR
  Q["问题"] --> V["向量检索 top-20"]
  Q --> B["BM25 检索 top-20"]
  V --> R["RRF 融合"]
  B --> R
  R --> TOP["取 top-4"]
`

项目实测： 结构感知切块 + 混合检索后，recall@1 50%→65%、recall@2 50%→100%。

① rerank 精排（关键概念：双塔 vs 交叉编码器）

- 双塔编码器（bi-encoder，召回用） ：问题和片段各自独立过 embedding，得到两个向量再算相似度——问题和片段 全程没直接交互 ，所以快（向量可提前算好存着），但精度有限；

- 交叉编码器（cross-encoder，精排用） ：把"问题+片段" 拼成一句话一起过模型 ，模型能看到两边逐字交互，打分远比双塔准——但每个候选都要单独过一遍，慢；

- 流程 ：双塔召回 top-20~50（快，别漏）→ 交叉编码器逐字打分 → 取 top-4。能救回"双塔因表达方式不同排在后面、其实高度相关"的片段；

- 类比：双塔像 HR 看简历标题快速筛选，交叉编码器像逐字读完再定。

② query 改写 ：解决两类问题—— 指代 （多轮里"它"指谁）和 用词差异 （用户口语 vs 文档术语）。三种做法：

- 指代还原 ：LLM 结合历史把"它修好了吗"改写为"1号分拣机过热修好了吗"再检索；

- 同义词扩展 ：把"发热"扩展成"发热/过热/温度升高"多路去查；

- HyDE ：先让 LLM 基于问题写一段"假设的标准答案"，再用它去检索——假设答案用文档风格写，和真实片段向量距离更近，命中率更高。

③ 多路召回 ：入库时给块打"路标"（标题/正文/表格），检索时三路并行各查 top-N，合并去重。为什么有效：问"备件安全线是多少"，答案在表格块里，单路正文检索可能让它排不进 top-4——单独表格路保证命中。实现：metadata 加 block_type，检索按 where 过滤。

④ 短文档不切 ：低于阈值整篇入块——短文档切了反而碎片化。项目里 _split_long_block ：内容不超块大小上限（×1.2）就整块用。

⑤ 其他 ：父子分块（小块检索命中准 + 大块喂 LLM 上下文完整）、分数治理（低分阈值兜底，防把不相关片段硬塞给模型）。

项目状态： ①~③⏳规划；④✅已实现。

- 索引参数 ：HNSW 的 M/efConstruction 调高提召回但费内存；IVF 的 nlist/nprobe 是速度/召回权衡——用评测集扫参；

- Embedding ：领域文本用中文优化模型（bge/m3e），数据量大可领域微调；

- 选型 ：小规模 Chroma（项目现状）；百万级/高并发/复杂过滤上 Milvus/Qdrant（分区+过滤）；

- 缓存 ：相同 query 短 TTL 缓存检索结果，知识库变更时主动失效；

- 一致性 ：hash 去重、按 source 增量更新、版本管理，防重复片段稀释结果。

评测集 = 固定的一组"问题 + 标准答案"。 recall@k = 前 k 个检索结果里包含答案的比例（20 题 recall@4=100% 即 20 题全部能在前 4 个结果找到答案）。

迭代方法： 每次只改一个变量 → 跑同一套评测集对比 → 看 badcase 定位问题环节（切块/embedding/检索/生成）。
