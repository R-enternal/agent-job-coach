# E · 实战问题与解决（Agent 开发踩坑全集）

面试最爱问"你遇到什么问题、怎么解决的"，每题的套路：现象 → 排查 → 方案 → 结果。

四层防御：

- 源头降选错概率 ：工具 description 写清"何时用、输入输出"；系统提示词写硬规则（知识类关键词必须走检索）；

- 降随机 ：temperature=0；

- 参数兜底 ：默认值 + schema 约束，模型漏传不崩；

- 失败回传自纠错 ：try/except 把错误文本回填，模型换参数重试或换工具。

验证： 评测"工具调用准确率"（期望工具 vs 实际调用），改 description 后回归对比。

①步数上限（项目 6 步，条件边强制 END）；②正确的终止条件（无 tool_calls 即结束）；③异常回退（失败回传让模型换路）；④工具去重/幂等 + 成本熔断。

金句： "循环不是 bug，没边界的循环才是——显式上限 + 状态可见（LangGraph 每步可审计）是工程化底线。"

可能原因五类：

- LLM 随机性 ：temperature 非 0、模型版本漂移；

- 上下文不稳定 ：历史长度不同、RAG 检索片段不同、prompt 混入动态内容；

- 工具层 ：返回的是实时数据（两次查自然不同，属"合理波动"）、执行顺序/并发竞态；

- 编排层 ：ReAct 路径不同（第一次调 1 个工具，第二次调 3 个）；

- 判定口径 ："85℃"和"85 摄氏度"等价但判定不认 → 假不稳定。

记录方法： 同一任务跑 5~10 次统计一致率；全链路 trace（最终 Prompt、检索片段、LLM 输入输出、tool_calls、耗时）用请求 ID 串起来；记录 prompt/模型/知识库/代码版本；badcase 归类。

解决： temperature=0；相同 query 缓存检索；prompt 去随机动态内容；结构化输出约束；判定同义归一化；先定义"稳定"标准（关键结论一致即可，不要求逐字）。

现象：AGV 充电温度答 45℃、手册是 35℃。解决：RAG 提供事实依据 + 提示词"只依据资料回答，找不到就说资料中未提及"+ temperature=0。实测 35%→100%。

MemorySaver（图内状态）+ Redis JSON 持久化（7 天 TTL 跨重启恢复），读取优先 Redis 兜底 MemorySaver。RedisSaver 因本机缺 RediSearch 模块用不了，所以自实现。

三层结构：

- 角色定义 ："你是仓脉智诊智能运维助手，帮助仓储管理人员查询设备运行状态。"——限定领域/服务对象/职责边界（也是防注入第一道）；

- 行为原则 ：不编造数据；工具结果用简洁中文总结；无关问题礼貌说明；回答保留设备名/数值/状态/时间；

- 工具规则 ：知识类关键词（怎么排查/手册/保养）→ 必须 retrieve_knowledge；实时业务查询 → 业务工具；复合问题 → 先知识后业务。

能力清单（8 工具）： 设备台账、健康度、告警、工单、备件、忙闲窗口、融合诊断、知识检索。工具 description 本身就是 Prompt，决定选工具准确率。

设计原则： 角色定边界、原则定底线、规则定选择、清单定能力——可控制、可评测、可扩展。

核心理念：不是玄学改词，是"目标→评测→迭代"的工程方法。

- 先定义"好" ：建评测集（项目=20 题，答案可溯源）；

- 搭基线 ：先跑当前效果（项目基线=裸答 35%）；

- badcase 驱动 ：看错题定位环节——没检索到（检索问题）/检索到没用上（Prompt 问题）/格式问题；

- 单变量迭代 ：一次只改一处，跑同一套评测集对比（A/B 测试）。

手法： 负向约束比正向描述有效（"找不到就说未提及"）；"应该"改"必须/禁止"；工具 description 也是 Prompt；temperature=0；上下文组织"系统指令→资料→问题"用分隔符隔离。

案例： 模型答 45℃（手册 35℃）→ 排查发现检索有答案、是模型没被约束 → 加"只依据资料回答" → 35%→100%。

七类边界：

金句： "边界处理是给不确定性画线——职责管该不该答，工具管能碰什么，循环管会不会失控，数据管答错了怎么办，异常管挂了怎么兜底。"
